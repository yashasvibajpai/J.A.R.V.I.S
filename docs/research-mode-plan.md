# JARVIS CLI deep research plan

**Proposed · 20 November 2026 · Baseline commit `8197546`**

Add an open-ended deep research mode that survives terminal exit and continues while there is relevant work worth doing. Let the agent stop when the evidence is sufficient or useful lines of inquiry are exhausted. Let the user read work in progress, redirect the investigation, challenge a finding, edit its documents, or stop it at any point. Preserve the existing tick-based brief and share configured free-provider allowances with foreground JARVIS features.

The CLI now includes the detached tick worker, deep investigation, live steering, citation review, dashboard, and revisioned document workspace. Use `/research doc help` for document commands, `/research publish <id>` for a readable briefing, and `/research diagnose <id>` for run diagnostics. PDF export is built in. PDF text extraction uses `pdftotext` or falls back to PDFKit on macOS. The evaluation section describes the remaining live quality and curiosity measurement work.

## Baseline behavior and gaps

The CLI starts an in-process worker with a 3.5-second heartbeat and persists missions and steps in SQLite. It supports list, status, pause, resume, and cancel. The usual run is six steps and six successful model calls, with three searches requesting five results each. The planner defaults to technology, market, and commercialization questions and hard-codes 2026, even for unrelated topics. The heartbeat controls when work starts. Mission duration and evidence quality have no explicit budget or stopping policy. [CLI startup](../packages/api/src/cli/jarvis-cli.ts#L96), [mission scheduler](../packages/api/src/engine/ResearchEngine.ts#L66), [decomposition](../packages/api/src/engine/ResearchEngine.ts#L251)

Model-produced URLs are accepted without matching them to retrieved results. | A plausible claim can acquire an invented citation. The CLI counts stored findings as facts verified. An offline smoke check against the actual engine and in-memory SQLite confirmed six steps, three searches and six model calls with stubbed providers. It also confirmed that an invented URL was stored, the reconciliation was absent from the writer's prompt, and a stale running synthesis step could produce a completed mission without a report. Live provider latency and report quality still need a measured baseline.

## Proposed CLI

| Command | Behavior |
| --- | --- |
| `/research <topic>` | Run the existing tick-based brief with improved citation checks and provider accounting. |
| `/research -d <topic>` | Queue an open-ended investigation with durable evidence and documents. Use `-d -- <topic>` for topics that start with flags. The long form `--depth deep` remains supported. |
| `/research dashboard [id]` | Open the tabbed research monitor. Select the active mission by default and switch between missions from the dashboard. |
| `/research status [id]` | Show the current branch, coverage, unresolved contradictions, pending instructions, latest document revisions, and any quota wait or completion reason. |
| `/research sources <id>` and `/research report <id> [document-id]` | Inspect source provenance and open the latest readable checkpoint or finished document. |
| `/research steer <id> <instruction>` | Give a natural-language instruction while the mission runs, such as “Focus on factory qualification” or “Explore what grid interconnection can tell us about delays.” |
| `/research fact-check <id> <claim-id or quoted claim>` | Reopen and prioritize a finding. Accept a proposed correction or source with the instruction and show what the evidence establishes. |
| `/research stop <id>` | Stop scheduling discovery, fence in-flight research, and publish the latest committed material with unresolved items clearly marked. |
| `/research reopen <id> [instruction]` | Continue a stopped or completed investigation from its existing evidence and document history. |

Keep list, pause, resume, and cancel. Pause holds the mission at a checkpoint for later resumption. Cancel terminates the workload and retains already committed material. Stop explicitly publishes a snapshot. Add the controls to help. Confirm scope interactively only when ambiguity would materially change the investigation. Otherwise record the inferred scope and let the user correct it.

### Tabbed research dashboard

Use the existing `/ask` form as the interaction reference. Reuse its terminal styling and keyboard conventions, with a persistent tab bar, a visible focus indicator, and key hints. The mission picker lists running, queued, paused, and quota-waiting missions first, with recent finished missions available for review. A mission launch prints its dashboard command. [Tabbed question form](../packages/api/src/cli/terminal-ui.ts#L221), [existing key handling](../packages/api/src/cli/terminal-ui.ts#L399)

| Tab | What it shows |
| --- | --- |
| **Overview** | Mission topic and state, current action, priority question coverage, unresolved claims, last checkpoint, and next eligible retry or finish reason. Pin dispatched calls and token usage at the top. |
| **Activity** | Recent and next actions, including breadth, depth, and related leads, with short rationales and outcomes. Include steering events, retries, quota holds, and checkpoint history. |
| **Evidence & Reports** | Read current findings and verdicts, inspect citations, and open working notes and latest document revisions while the mission runs. |
| **Usage** | Mission totals and a breakdown by provider, model, and phase. Show calls dispatched, outcomes such as successful, failed, rate-limited, or in flight, and retries as a subset of attempts. Show input and output tokens when available, plus provider-reported totals if the split is unavailable. Show search requests and shared provider headroom separately. |
| **Controls** | Pause, resume, or stop and publish the latest checkpoint. Enable actions for the selected mission state and show when a command is queued, applied, or failed. For stop, confirm which mission will publish and make the resulting snapshot easy to open. |

Use `Tab` / `Shift+Tab` or left / right arrows to switch tabs, up / down arrows to navigate items, and `Enter` to inspect or activate. Keep Pause, Resume, and Stop visible in the Controls tab and discoverable from the status footer. `Esc` returns to chat while the worker continues. Use text status labels and focus markers that work without color, adapt to narrow terminals, and expose the same information and actions through plain-text slash commands in non-interactive sessions. Include usage in `/research status [id]` for the plain-text path.

Refresh from committed SQLite state on a lightweight local poll so viewing the dashboard consumes no API capacity. Preserve the selected mission, tab, and scroll position during refresh. Coordinate terminal ownership with the REPL, route background notifications into the dashboard while it is open, and restore cursor, raw mode, and input listeners on exit or failure. Display a stale checkpoint or unavailable worker explicitly. Send controls through the same persisted commands used by slash commands and refresh from the worker's acknowledgement. [REPL notifications and input](../packages/api/src/cli/jarvis-cli.ts#L296)

### Per-mission model usage

Add usage metadata to the provider adapter boundary while preserving existing text callers. Persist one row per outbound model attempt with a stable attempt ID, mission and action IDs, provider and model, outcome, retry relationship, and available token counts. Count dispatched retries and fallbacks individually, starting when the call is sent. Keep never-dispatched reservations outside the call count. Reuse attempt IDs for quota reconciliation so restarts and late responses cannot double-count usage. Include planning, extraction, verification, synthesis, and model-assisted document edits performed for that mission. [Text-only adapter interface](../packages/shared/src/adapters/LLMProvider.ts#L48), [existing streaming estimate](../packages/api/src/engine/SmartRouter.ts#L339)

Prefer provider-reported input, output, and total tokens. Show estimates separately when only prompt or output text is available, and mark attempts with no defensible count as unknown. If a provider reports cached or reasoning tokens, identify them as breakdowns and apply that provider's counting semantics to avoid adding them twice. Display mission consumption separately from the quota ledger's conservative reservations and from other JARVIS sessions. Legacy missions without measurements show usage unavailable.

### Steering a live mission

- Persist each instruction before acknowledging it. Store its sequence, target question, claim or document, and state such as queued, applied, or needs clarification. Apply steering before selecting the next action and while the mission is waiting for quota. Show which branches moved up, were added, or were deferred.
- Interpret “focus” as reprioritization, “explore” as a new linked question, and an explicit scope change as a revision to the research brief. Preserve existing evidence for later use. Version the plan so older in-flight work cannot write into superseded sections or promote a stale conclusion.
- A fact-check marks a claim under review, reopens source passages, seeks independent evidence, and records whether the correction was confirmed, qualified, or remained unresolved. Preserve the old claim revision and flag every document that used it. Update current affected sections with a visible correction once verified. Historical exports retain their revision labels.
- Make stop effective from running, paused, or quota-waiting state. If stop arrives during a request, abort it where supported and fence later results. Use a local render of committed notes and evidence if no model call is available. Include instructions or checks that were still pending when the user stopped.

## Investigation loop

1. **Plan.** Turn the topic into ranked questions with an as-of date, scope, and explicit coverage criteria. For each important question, record what evidence could answer it and what would change the current conclusion.
2. **Discover and read.** Start with `WebSearchService` for discovery. Open the original HTML or PDF, follow references to their origin, and read the relevant section, table, or methods. Use alternate queries or sources when a page is inaccessible. Record that gap and keep snippets as leads. Assess authority, relevance, recency, method, and incentives in the context of each claim.
3. **Update the evidence.** Extract atomic claims and tie them to a retrieved passage. Track supports, contradicts, and qualifies relationships. Normalize dates, units, definitions, and populations before deciding whether claims disagree. Group syndicated copies, press-release rewrites, and articles drawing on the same underlying study as a single evidence family.
4. **Replan.** After each completed action, update the plan from the new evidence and any user instructions. Reassess options across breadth, depth, and relevant tangents. Require each follow-up to name the question or claim it could change and what a useful result would look like. Deduplicate near-identical queries and avoid re-reading unchanged documents unless a different passage could settle an open issue.
5. **Verify and write.** Send decisive claims, retrieved excerpts, and conflicting evidence to a separate verification pass. Check quotation and locator integrity, whether the passage supports the wording, and whether numbers, dates, and scope match. Synthesize from the reviewed ledger, then audit the draft's claim links and substantive assertions before publishing.

For example, if several articles report a battery factory is operating and all trace back to the same announcement, follow the announcement and seek independent evidence of production. A commissioning record may confirm installation while leaving commercial shipments unverified. The report should retain that distinction and cite the underlying records.

### Curiosity across breadth, depth, and adjacent domains

Use three behaviors inspired by observed patterns in human information seeking. Zhou and colleagues found evidence of broad scouting, targeted pursuit, and creative jumps across concepts in Wikipedia reading trails. Use that study as design inspiration and validate the resulting behaviors on research tasks. [Architectural styles of curiosity in global Wikipedia mobile app readership](https://doi.org/10.1126/sciadv.adn3268)

| Behavior | What the agent does |
| --- | --- |
| **Breadth** | Map the main dimensions of the topic, look for missing perspectives and evidence types, and sample several distinct branches before allowing the most visible one to dominate. Revisit the map when a new finding exposes a gap. |
| **Depth** | Follow references through to original records, inspect methods and definitions, check dates and units, compare independent accounts, and seek evidence that could overturn the leading interpretation. Return to earlier claims when new evidence qualifies them. |
| **Relevant tangents** | Follow an analogy, shared mechanism, surprising dependency, or nearby domain if it offers a test or explanation for the original question. Write down the connection and expected payoff before probing it. Continue when the probe returns a new source, useful test, or material insight. Park weak branches with the reason and let new evidence or the user reopen them. |

Keep a persistent map linking questions, branches, claims, and sources. For each candidate action, log a short rationale and rate question importance, uncertainty, likelihood of shifting the answer, independence or novelty of the evidence, and effort. Favor neglected core questions, disconfirming evidence, and high-value unexpected leads when their signals warrant it. A finding on battery commercialization might justify a tangent into grid interconnection records if power availability plausibly explains a delay. A general search on energy policy would need a more specific connection to earn a follow-up.

### Evidence-based stopping

- At each checkpoint, assess whether each priority question is answered with adequate evidence, disputed, or open. An answered question meets the verification criteria agreed in the plan. Open questions retain the missing evidence and plausible next paths.
- Close a branch when the evidence answers the question, when further material would have little bearing on the user's request, or when credible alternative paths have been attempted and have yielded only duplicate or immaterial results. For consequential uncertainties, check a genuinely different source family, method, or search route when one is viable before closing the branch.
- As a starting heuristic, use two consecutive completed evidence reviews with no material change as a signal to reassess. Material change includes a new priority answer, an independent corroboration, a verdict change, or a useful new thread. A stalled query or quota delay supplies no evidence of saturation. Newly relevant evidence or user steering can reopen closed branches.
- Finish when priority questions are sufficiently covered and no promising follow-up remains. Finish with explicit gaps when the remaining paths are exhausted. Record the stop reason, unresolved questions, and why remaining leads were deferred. Check that there is no unapplied instruction before committing an autonomous finish.
- Elapsed time and request counts are status and diagnostic information. Free quotas can delay work across successive reset windows. If a required source or provider is unavailable with no known retry, checkpoint and show what is blocked. Leave the decision to stop or continue available to the user.

### Evidence and output

Extend `SQLiteResearchStore` with versioned, mission-scoped records for questions, actions, retrieved documents, passages, claims, claim–evidence links, and report revisions. Give each source a resolved URL or document identifier, publisher, publication and retrieval dates, version or content hash, retrieval status, and origin family. Give each passage a document version, exact excerpt, and page, section, or table locator. Record the outcome of each action, including retrieval failures and what changed in the investigation. Select relevant passages and claims per question to keep model context bounded.

Use explicit claim verdicts such as **corroborated**, **single-source**, **disputed**, and **insufficient evidence**. Require two independent evidence families to call a consequential claim corroborated. A sole authoritative record can establish what that authority published or decided, with attribution. Retain disagreement that cannot be resolved and label analytical inferences with their supporting premises. Generate citations in code from stored IDs and fail validation on unknown IDs, missing locators for quoted material, or citations to unread pages. Check semantic support separately because valid IDs alone cannot establish it.

### Research documents and exports

Give each mission a workspace with multiple named documents. The agent can create a briefing, source notes, timelines, claim tables, or separate topic reports as the investigation develops. Each document has a stable ID, an ordered set of sections, revision history, and links to claims and sources. Make Markdown and PDF available independently or together. Offer a structured research bundle containing the chosen document revisions, question map, evidence index, and correction history.

| Operation | Behavior |
| --- | --- |
| `/research doc list <id>` and `/research doc show <id> <document>` | List the workspace and open any committed document or revision while research runs or after it stops. |
| `/research doc help` | Open a tabbed guide to document commands with explanations, syntax, and examples. |
| `/research doc new <id> <title>` | Create a named document, optionally from selected notes, questions, or claims. |
| `/research doc append <id> <document> <instruction>` | Add material to a document or to a selected section. Accept user text or an instruction to draft from existing evidence. |
| `/research doc merge <id> <target> <sources…>` | Merge whole documents or selected sections into a named target. Preview the section order, repeated material, and citation conflicts. Keep input documents available. |
| `/research doc trim <id> <document> <section or range>` | Remove or condense selected content in a new revision. Support heading, section, and text selection. For a generated PDF, resolve page selections against the chosen PDF revision and preview the matched source blocks before regenerating it. |
| `/research doc export <id> <document> --format md,pdf` | Render a selected revision in the requested formats. Support multiple exports and a mission-level research bundle. |

Use the same managed document revision for editing and rendering across Markdown, PDF, and the research bundle. A PDF append, merge, or trim edits the source revision and renders a new PDF. For a PDF or Markdown file supplied by the user, import selected pages or sections into a working document and retain a reference to the original. Store document edits as revisioned operations with an expected base revision. If a user edit races with an agent update to the same section, keep both changes available, show the conflict, and require explicit resolution before overwriting the user's text. Let users inspect diffs and restore prior revisions.

Resolve citation links against the evidence ledger after every edit. Deduplicate repeat references when merging, preserve disagreements, and update reference numbering and the table of contents. Trimming a report removes material from that revision while retaining underlying research evidence and prior exports. Flag user-supplied assertions with no source as such. Publish labeled working checkpoints and verified final revisions with coverage, caveats, and open claims. Record an evidence snapshot ID with each revision so a later correction can flag affected documents without rewriting historical files.

Reuse `FileService` and `PdfService` for exports. Include mission, document, and revision identifiers in filenames, and make the PDF source URLs usable. Track PDF and GBrain outcomes separately. Gate GBrain indexing on the completed report audit and configured capture policy. [File export](../packages/api/src/services/FileService.ts#L60), [PDF rendering](../packages/api/src/services/PdfService.ts#L26)

## Long-running execution

- Keep the existing configurable tick loop and its 3.5-second default. On each eligible tick, claim at most one bounded research action, such as a query, a document open, an extraction, or a verification batch. Use the same scheduler for brief and deep missions. Give each runnable mission a turn and let the worker skip over missions waiting for quota. Keep the delay and host concurrency configurable.
- Run the scheduler in a separate local worker sharing the same SQLite database with the REPL. The worker continues after the REPL exits and resumes from durable checkpoints across restarts. The laptop must be awake while work runs. Preserve background notifications, status, pause, resume, cancel, and the current brief export workflow.
- Claim actions with a transactional lease and attempt token. Reclaim expired leases. Commit evidence, the next actions, and the completed checkpoint together. Use stable action and publication keys. Fence writes against stale attempts, superseded instructions, and mission state changes. Use per-attempt request deadlines and bounded retries for recoverable failures. Write exports atomically so failed renders and retries leave earlier files readable.
- Route research through a typed free-only `SmartRouter` policy. Use the same persistent quota gate for research, chat, streaming, embeddings, and other JARVIS paths when they share a credential, account, project, or model allowance. Keep provider and search limits configurable to match the account's actual free plan. Treat the constants in `provider-registry.ts` as local defaults and verify them during implementation against configured accounts. Validate the model behind a configurable alias before admitting it to the free-only pool. [Router limits](../packages/api/src/engine/SmartRouter.ts#L116), [provider defaults](../packages/api/src/engine/provider-registry.ts#L132)
- Reserve capacity transactionally before each outbound attempt in every applicable quota window. Account for requests, input and output tokens, search credits, and provider-specific windows where applicable. Reconcile token reservations using returned usage where available and retain a conservative charge when a dispatched attempt has unknown usage. Include failed calls, retries, and search fallbacks. Disable hidden SDK retries where possible or make the adapter reserve capacity for every retry. Put Tavily and Brave calls behind the same mechanism when configured, and pace public search and document opens by host. [Search fallback chain](../packages/api/src/services/WebSearchService.ts#L57)
- Honor provider reset times, `Retry-After`, and configured or reported remaining limits. Persist a shared cooldown and next eligible time. If a call cannot be reserved, leave it queued and report the reason. Use another eligible free provider only if it can perform that action. Keep local controls and snapshot export available during waits. Account for other consumers sharing the same API credentials where the provider exposes remaining capacity.
- Treat fetched documents as untrusted data. Limit request and parser resources, allow public HTTP(S) retrieval, and check destination addresses and redirects before fetching.

## Measuring curiosity and quality

*Agents Explore but Agents Ignore* distinguishes encountering an unexpected useful clue from acting on it. Adapt the intervention to a controlled document corpus with a discoverable lead, a matched version with the lead removed, and tempting but irrelevant distractors. *Why Did Apple Fall* pairs model self-reports with behavioral tests and finds selected gains from curiosity-inspired questioning. For JARVIS, score observable follow-up and evidence use. The November 2026 position paper *Sampling Is Not Curiosity* proposes a stronger framing around persistent online learning about actions. Treat a per-mission model of expected source yield, updated after each action, as a later experiment. [Environmental curiosity study](https://arxiv.org/abs/2604.17609), [ACL behavioral study](https://aclanthology.org/2026.findings-acl.1954/), [NeurIPS position paper](https://arxiv.org/abs/2611.10501)

Use WebThinker as a reference for gap-driven navigation. Adapt DeepResearch Bench's citation assessment, and score information retrieval, analysis, and presentation with task-specific rubrics as in DeepResearch Bench II and ResearchRubrics. Use deterministic checks where possible and blind human review for a sample of semantic judgments. [WebThinker](https://papers.nips.cc/paper_files/paper/2025/file/ae03bdef276132fae089692445725635-Paper-Conference.pdf), [DeepResearch Bench](https://arxiv.org/abs/2506.11763), [DeepResearch Bench II](https://arxiv.org/abs/2601.08536), [ResearchRubrics](https://openreview.net/pdf/98ceac9b91e6890ca29a19c1b6d1efeeaab29f98.pdf)

| Metric | How to score it |
| --- | --- |
| Lead discovery, follow-through, and use | Measure discovery over eligible seeded leads, follow-through over discovered leads, and correct conclusion changes or evidence-backed decisions to retain the conclusion. Track irrelevant follow-ups separately. |
| Breadth, depth, and tangent usefulness | Count distinct rubric-required perspectives covered, consequential claims traced to original sources and independently tested, and tangents that produce relevant evidence, a better explanation, or a useful test. Record off-topic branches separately. |
| Evidence quality | Measure citation support over cited claim–source pairs, citation coverage over all substantive report claims, and verified priority questions over all priority questions. Audit whether sources are independent and whether contradictions were resolved correctly or disclosed. |
| Stopping quality | Measure premature stops with a discoverable priority answer, repeated work after evidence saturation, and correct handling of blocked sources. Compare checkpoint quality and evidence gained per action. |
| Steering and document integrity | Measure feedback applied by the next eligible decision, correction propagation to current documents, citation preservation across edits, revision conflict recovery, and stop behavior while a request or quota wait is in progress. |
| Operational reliability | Measure time to first useful checkpoint, runtime, resume success, and concurrent-worker behavior. Test quota enforcement across restarts, chat and research contention, shared aliases, failed calls, SDK retries, search fallbacks, and reset windows. |
| Dashboard and usage accuracy | Test keyboard navigation, narrow and colorless output, terminal restoration, and live updates while switching missions. Compare displayed attempts and tokens with provider fixtures, including retries, unknown usage, quota blocks, and worker restart. Exercise pause, resume, and stop from the dashboard and plain-text commands. |

Compare the current pipeline, a fixed-query workflow with document retrieval, the adaptive workflow, and the adaptive workflow with verification disabled. Use the same models and tools for the fixed versus adaptive comparison. Compare reports at equal action counts in the harness to measure efficiency, and run separate uncapped cases to evaluate stopping decisions. Start with frozen cases for copied sources, corrected numbers, ambiguous units, inaccessible originals, planted cross-domain leads and distractors, and irreducible disagreements. Add a small live-web set for search and retrieval drift. Set thresholds after baselining. Initial pilot targets are at least 95% human-audited citation support, a 15-percentage-point gain in useful lead follow-through at matched work, zero unknown citation IDs, zero configured quota overruns, and zero false completions in interruption tests.
